Lesson 01

How Python Runs and How Projects Start

From source files and environments to predictable command-line tools

The Big Picture

As a C# or Java developer, you already know that source code is not normally executed as raw text. Python has the same broad shape, but its vocabulary and defaults are different. A Python program is source text that an implementation such as CPython compiles to bytecode and executes in a Python virtual machine. A project also needs a repeatable environment and an explicit process contract.

┌──────────────────┐ ┌──────────────────┐ ┌────────────────────┐ │ .py source files │ ──→ │ compiler │ ──→ │ Python bytecode │ │ modules/packages │ │ (often implicit) │ │ cached when useful │ └──────────────────┘ └──────────────────┘ └─────────┬──────────┘ │ ▼ ┌────────────────────┐ │ Python VM/runtime │ │ names, imports, I/O │ └─────────┬──────────┘ ▼ operating-system process
🧠 Key Concept: Implementation, not mythology

This lesson describes the common CPython model. “Python” is a language specification with multiple implementations; bytecode details and execution strategies are implementation details, not promises that every Python implementation must share.

Source, Bytecode, and the Runtime

When CPython imports a module, it parses the source, compiles it to an internal bytecode form, and executes that bytecode. CPython may cache imported-module bytecode in __pycache__ to reduce repeated compilation, but you should not treat a .pyc file as a portable executable or as a stable public format. The important mental model is that Python manages compilation and execution for you at runtime.

Scripts, Modules, Packages, and Distributions

A script is a Python file you invoke as a program. A module is an importable Python file. The same file can serve both roles when it keeps reusable definitions at module scope and puts program startup behind a guard:

def build_manifest(source_dir):
    """Return data for a later export step."""
    return {"source": source_dir, "files": []}


def main():
    print(build_manifest("assets"))


if __name__ == "__main__":
    main()

Running python manifest.py sets __name__ to "__main__", so the startup code runs. Importing the module gives it its module name, so the startup code does not run automatically. A package is an import namespace formed from one or more modules. A distribution is what you install and publish; it can contain one or more import packages.

⚠️ Python Surprise: Importing can execute code

Importing is not merely a header declaration. Python executes a module's top-level statements the first time it loads it in a process. Keep expensive work and command-line behavior behind functions and the __main__ guard.

Projects, Environments, and pyproject.toml

A virtual environment is an isolated installation context for a project. It keeps one project's interpreter and installed packages from silently changing another project's behavior. uv is a fast tool for creating environments, resolving dependencies, and running commands; it is a tool choice, not a language requirement.

uv init asset-audit
cd asset-audit
uv venv
uv add rich
uv run python main.py
uv run python -c "print('environment works')"

The exact files created by uv init can vary with its options and version, but the project should have a pyproject.toml describing metadata and dependencies. Committing that declaration gives collaborators and automation a source of truth; the local .venv directory itself is normally not committed.

💡 Important: Choose the interpreter explicitly

“It works on my machine” often means a different interpreter or dependency set. Prefer uv run ... (or an explicitly selected virtual-environment interpreter) when documenting commands for a pipeline tool.

Command-Line Contracts: Streams and Exit Codes

Every command-line process has three conventional streams: stdout for normal results, stderr for diagnostics, and an exit code for success or failure. A useful tool can be redirected or called by another process because it keeps those channels meaningful.

┌────────────────────┐ stdout ───────→ results / next tool │ Python process │ │ │ stderr ───────→ human-visible diagnostics │ return from main │ exit code ─────→ 0 success, non-zero failure └────────────────────┘ 
import sys


def main():
    if len(sys.argv) != 2:
        print("usage: audit.py ROOT", file=sys.stderr)
        return 2
    print(f"Auditing {sys.argv[1]}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

raise SystemExit(code) asks the process to finish with that status. This is the Python equivalent of returning a status from a C# or Java entry point, although Python's ordinary top-level script does not require a Main method.

💚 Technical-Art Relevance

An asset validator, texture converter, or DCC bridge is easier to automate when it prints machine-readable results to stdout, explains failures on stderr, and returns non-zero on failure. That contract works from a terminal, CI job, editor button, or subprocess caller.

Short Drills

  1. Write a module with one reusable function and a main() guarded by if __name__ == "__main__". Import it from a second module and verify that startup does not run during import.
  2. Create a small uv project and run it with uv run python -m .... Record which files describe the project and which local files are environment state.
  3. Make a command that prints one normal result, one diagnostic to stderr, and exits with status 2 for invalid arguments.

Key Takeaways

  • Runtime model: CPython commonly compiles source to bytecode and executes it in its runtime.
  • Import model: modules are executable namespaces; use the main guard to separate reusable code from startup.
  • Project model: virtual environments isolate dependencies, while pyproject.toml declares project metadata.
  • Process contract: stdout, stderr, and exit codes make automation composable.
