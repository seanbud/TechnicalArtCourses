Lesson 08

Async, Threads, Processes, and Deployment Mental Models

Formal grounding for coroutine scheduling, shared-state workers, process isolation, and deployment

The Big Picture

Imagine one technical artist coordinating three kinds of work: waiting for a network response, processing a CPU-heavy mesh, and updating a desktop UI. “Concurrent” means work overlaps in time; “parallel” means work executes simultaneously on different execution resources. Async tasks, threads, and processes create those overlaps differently. Choosing one because it sounds fast is how pipelines become unreliable.

┌──────────────────┐ cooperative await ┌──────────────────────┐ │ event-loop thread│ ─────────────────────────→ │ task A: waiting I/O │ │ │ ←───────────────────────── │ task B: ready │ │ runs one task │ resume another task └──────────────────────┘ └──────────────────┘ ┌──────────────┐ shared memory ┌──────────────┐ │ main thread │ ◄──── lock / queue ─────► │ worker thread│ └──────────────┘ └──────────────┘
🧠 Key Concept: Scheduling is not parallelism

An event loop can interleave waiting tasks on one thread. Threads can overlap work while sharing a process. Processes have separate memory and can provide stronger isolation. None of these labels alone guarantees faster CPU-bound execution.

Coroutines, await, Tasks, and the Event Loop

An async def function is a coroutine function. Calling it creates a coroutine object; it does not run the body to completion. Awaiting that coroutine runs it until it returns or reaches an awaitable suspension point. A task schedules a coroutine on an event loop so other tasks can run while it awaits I/O.

import asyncio

async def fetch_manifest(name):
    await asyncio.sleep(0.01)  # stand-in for non-blocking I/O
    return {"name": name, "ok": True}

async def main():
    first = fetch_manifest("hero")       # coroutine object; not finished
    result = await first                  # run and receive its result
    tasks = [
        asyncio.create_task(fetch_manifest(name))
        for name in ("tree", "camera")
    ]
    return result, await asyncio.gather(*tasks)

asyncio.run(main())

await is an expression that produces the coroutine's result; it is not a background-thread command. create_task asks the running loop to schedule work. Cooperative suspension means a coroutine must reach an await point; a blocking file operation or long CPU loop can still freeze every task sharing that event-loop thread.

Concurrency, Parallelism, and CPU Work

Async is excellent for many operations that spend time waiting: network requests, timers, or an API that provides an async interface. It does not make a CPU-heavy mesh decimator parallel by itself. Standard CPython builds use a global interpreter lock (GIL) that limits simultaneous execution of Python bytecode in multiple threads; free-threaded builds exist, but they are not the assumption to make for a portable course or pipeline.

⚠️ Python Surprise: async does not move work to another thread

Declaring a coroutine does not create a worker. It creates a schedulable operation whose progress depends on an event loop and explicit suspension points. Use an executor or a process strategy when blocking or CPU-heavy work must leave the loop.

Threads, Shared State, Locks, and Queues

Threads live in one process and can read the same objects. That makes communication cheap, but it also creates races: one thread can observe a partially updated state or two threads can overwrite each other's changes. The GIL does not make a multi-step business operation automatically atomic, and it does not make every library thread-safe.

from queue import Queue
from threading import Thread

def worker(jobs, results):
    while True:
        job = jobs.get()
        if job is None:
            jobs.task_done()
            return
        results.put(job.upper())
        jobs.task_done()

jobs = Queue()
results = Queue()
thread = Thread(target=worker, args=(jobs, results))
thread.start()
jobs.put("tree.fbx")
jobs.put(None)
jobs.join()
thread.join()

A lock protects a critical section when shared mutation is necessary. A queue is often clearer: the main thread owns orchestration, workers receive messages, and results return through another queue. In a desktop tool, keep UI calls on the thread required by the UI framework and send data back rather than touching controls from arbitrary workers.

Processes, Private Memory, and IPC

A process has its own interpreter state and private address space. A child process does not automatically see the parent's Python objects. Data must cross an inter-process communication boundary, such as a pipe, queue, socket, or serialized file. That boundary costs time, but it also isolates crashes and can enable true parallel CPU work.

┌─────────────────────┐ serialize / IPC ┌─────────────────────┐ │ parent process │ ──────────────────────→ │ worker process │ │ orchestration/UI │ ←────────────────────── │ CPU-heavy operation │ └─────────────────────┘ result / error └─────────────────────┘ private memory private memory

Use a process pool when jobs are independent and their inputs and outputs can be serialized. Avoid assuming that a large in-memory scene graph will be cheap to send to every worker. The process start method and external libraries also matter, so test the deployment platform rather than relying on a desktop-only experiment.

Servers and Desktop Deployment

A Python server is a long-lived process that accepts requests, performs work, and returns responses. An async server can use an event loop for many I/O-bound connections; a worker model may use threads or processes for blocking or CPU-heavy work. A desktop automation tool has a different contract: it needs a launch command, configuration location, logging, external executable discovery, and a clean shutdown path.

💡 Important: Deployment preserves the mental model

Package the same decisions you made locally: which interpreter runs, which dependencies are installed, whether work is async/I/O-bound or CPU-bound, how workers communicate, and how errors reach the operator. A server framework or executable wrapper cannot remove those architectural choices.

💚 Technical-Art Relevance

Use async for concurrent service calls, threads for carefully bounded I/O or UI-adjacent work, and processes for isolated CPU-heavy conversions. Send records across boundaries, not shared assumptions about objects, and measure before choosing a model.

Short Drills

  1. Label each example as async concurrency, threaded work, or process isolation: waiting on three HTTP calls, updating a UI from a worker, and decimating four large meshes.
  2. Write down the difference between creating a coroutine object, awaiting it, and scheduling it with create_task.
  3. Draw the memory boundary between a parent and process worker. Name one IPC format suitable for a small asset record.
  4. Identify a shared-state race in a threaded asset queue and redesign it around a lock or message queue.

Key Takeaways

  • Coroutine: calling async def creates an object; await runs it to a result, and a task schedules it.
  • Event loop: cooperative suspension enables I/O concurrency, not automatic CPU parallelism.
  • Threads: share memory, so protect shared state and respect thread-unsafe APIs.
  • Processes: isolate memory and communicate through explicit IPC, trading overhead for isolation and CPU scaling.
  • Deployment: package the interpreter, dependencies, worker model, configuration, and shutdown/error contract together.
