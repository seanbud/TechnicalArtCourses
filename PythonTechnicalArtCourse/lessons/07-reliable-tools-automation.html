Lesson 07

Reliable Tools and Automation

Exceptions, command-line contracts, subprocesses, and deliverable-minded packaging

The Big Picture

An automation tool is a production worker: it receives inputs, performs steps, reports what happened, and leaves a result that another person or process can trust. Reliability does not mean catching every error and continuing. It means classifying failures, preserving useful context, using narrow recovery paths, and exposing a clear command-line contract.

┌──────────────┐ parse inputs ┌──────────────┐ external tool ┌──────────────┐ │ CLI process │ ───────────────→ │ Python step │ ────────────────→ │ child process│ │ argv / env │ │ try/except │ │ DCC / build │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ stdout / stderr / exit code │ errors + cleanup │ return code └─────────────────────────────────┴──────────────────────────────────┘
🧠 Key Concept: Failure is part of the interface

A reliable tool makes invalid input, missing dependencies, conversion failure, and unexpected bugs distinguishable. Exceptions are for Python control flow; stdout, stderr, and exit codes are for the process boundary.

Exceptions, Tracebacks, and Custom Errors

An exception interrupts ordinary control flow and carries a traceback showing where the failure propagated. Catch the narrowest exception you can handle. A broad except Exception can be appropriate at a top-level boundary for logging and a non-zero exit, but it is a poor substitute for local recovery rules.

class ConversionError(Exception):
    """The source was readable but could not be converted."""


def read_dimensions(record):
    try:
        width = int(record["width"])
        height = int(record["height"])
    except (KeyError, ValueError) as error:
        raise ConversionError("invalid dimensions") from error
    else:
        return width, height
    finally:
        print("dimension lookup finished")

else runs only when the protected work succeeds. finally runs whether it succeeds or raises, so use it for cleanup or a small unconditional observation, not for accidentally hiding an original failure. raise ... from error preserves the cause while presenting a domain-specific error to the caller.

⚠️ Python Surprise: A catch can make failure invisible

Do not catch an exception, print “failed,” and return a successful result. Either recover deliberately, re-raise with useful context, or let the top-level boundary convert the failure into a non-zero process status.

CLI Inputs, Streams, and Exit Status

sys.argv exposes raw command-line strings. It is useful for tiny scripts, but argparse provides named options, conversion, help text, and consistent invalid-argument behavior:

import argparse
import sys

def parse_args():
    parser = argparse.ArgumentParser(description="convert one asset")
    parser.add_argument("source")
    parser.add_argument("--output", required=True)
    parser.add_argument("--dry-run", action="store_true")
    return parser.parse_args()

def main():
    args = parse_args()
    print(f"source={args.source} output={args.output}")
    if args.dry_run:
        print("dry run", file=sys.stderr)
    return 0

if __name__ == "__main__":
    raise SystemExit(main())

argparse normally writes usage errors to stderr and exits with a non-zero status. For your own application failures, return a status from main and raise SystemExit. Keep normal results on stdout and diagnostics on stderr so a parent process can capture them separately.

💡 Important: Make the command composable

Document the required inputs, output location, exit statuses, and whether paths are relative to the current working directory. A tool that works interactively but cannot be called predictably by CI or an editor is not automation-ready.

Subprocesses and External Tools

subprocess.run starts a child process and, by default, waits for it to finish. Popen gives you a handle for more involved interaction and returns before the child completes. The child has its own process state; it does not share Python objects with the parent.

from pathlib import Path
import subprocess

command = ["converter", "--input", "tree.fbx", "--output", "build/tree.gltf"]
completed = subprocess.run(
    command,
    cwd=Path("tools"),
    capture_output=True,
    text=True,
    timeout=60,
)

if completed.returncode != 0:
    raise RuntimeError(completed.stderr.strip() or "converter failed")
print(completed.stdout)

Passing an argument list avoids shell parsing and is the safer default. shell=True changes the command interpretation and should be reserved for a specific, understood shell requirement. A timeout stops waiting and raises TimeoutExpired; it does not guarantee that every descendant process in a tool's process tree has been terminated. Process-tree behavior and termination semantics vary by platform and by the child tool.

💚 Technical-Art Relevance

A DCC exporter or texture compiler is an external dependency, not a Python function call. Validate its executable, pass explicit paths, capture its output, check its return code, and preserve enough context to reproduce the failed command.

Packaging and Platform Deliverables

A deliverable includes more than the .py files: project metadata, dependency declarations, an invocation contract, configuration defaults, and platform assumptions. A pyproject.toml can declare a package and a console script entry point; a build tool can produce an installable wheel or source distribution. Whether you ship a wheel, a virtual environment, a standalone application, or a container depends on the target platform and deployment policy.

Do not promise that packaging removes every platform concern. Native libraries, DCC installations, licenses, environment variables, path conventions, permissions, and executable availability still need validation. A good release checklist runs the tool in a clean environment and records the exact interpreter and external tool versions.

Short Drills

  1. Define a custom error for a malformed manifest, catch only the parsing errors you can translate, and preserve the original cause.
  2. Build an argparse command with a required source and output, then state what belongs on stdout, stderr, and the exit code.
  3. Wrap a harmless external command with subprocess.run, capture its output, and describe what the parent knows if the child launches another process.
  4. Write a deliverable checklist that includes Python version, dependencies, external executables, working directory, and platform assumptions.

Key Takeaways

  • Exceptions: catch narrowly, add context with raise ... from, and keep cleanup in finally or a context manager.
  • CLI boundary: argparse, stdout, stderr, and exit codes make tools composable.
  • Subprocess: run waits by default; child and descendant lifecycle behavior is not magically uniform across platforms.
  • Delivery: packaging must include dependencies and external-tool assumptions, not just source files.
