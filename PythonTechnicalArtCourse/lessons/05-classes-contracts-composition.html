Lesson 05

Classes, Contracts, and Composition-First Design

Inheritance, protocols, duck typing, and choosing flat designs before clever hierarchies

The Big Picture

A class is useful when an object has state and behavior that belong together. A design becomes harder to change when every new behavior requires another level of inheritance. For technical-art tools, prefer small components with explicit contracts and compose them into a pipeline. Learn inheritance and multiple inheritance so you can read existing Python, but treat them as tools rather than the default architecture.

🧠 Key Concept: Program to a behavior contract

A caller often needs “something with convert(record),” not a specific base class. Python can express that expectation with a protocol or with duck typing, while composition lets you replace the implementation without changing the pipeline.

Classes, Instances, and Overrides

An instance carries data; a method provides behavior. Inheritance lets a subclass reuse a base implementation and override selected methods:

class Exporter:
    format_name = "generic"

    def export(self, record):
        raise NotImplementedError("subclasses must export")


class GltfExporter(Exporter):
    format_name = "gltf"

    def export(self, record):
        return f"{record['path']} -> .gltf"


exporter = GltfExporter()
print(exporter.format_name)
print(exporter.export({"path": "tree.fbx"}))

Method lookup finds the most specific implementation. super() calls the next implementation in the method-resolution order, which is particularly important when a subclass extends rather than replaces setup:

class LoggedExporter(GltfExporter):
    def export(self, record):
        print(f"exporting {record['path']}")
        return super().export(record)

This resembles a C# virtual method and base.Export(...), but Python's lookup rules become more significant when multiple base classes are involved.

Abstract Base Classes and Protocols

An abstract base class (ABC) makes a nominal contract explicit. A subclass must implement abstract methods before it can be instantiated:

from abc import ABC, abstractmethod

class Converter(ABC):
    @abstractmethod
    def convert(self, source, destination):
        """Convert one source asset."""
        raise NotImplementedError

class FbxConverter(Converter):
    def convert(self, source, destination):
        return f"convert {source} to {destination}"

A Protocol describes the shape a caller needs and is especially useful with static type checkers. A class can satisfy a protocol without inheriting from it:

from typing import Protocol

class Validator(Protocol):
    def validate(self, record) -> list[str]: ...

class TextureValidator:
    def validate(self, record) -> list[str]:
        return [] if record["width"] > 0 else ["width must be positive"]

def publish(record, validator: Validator):
    return validator.validate(record)

This is close to a C# interface in purpose, but a protocol is primarily a structural typing contract. The static checker looks for the required members; ordinary Python does not automatically enforce every annotation at runtime.

💡 Important: Separate the contract from the construction

Use an ABC when shared implementation or nominal registration is valuable. Use a protocol when callers only need a shape. Keep the runtime boundary explicit: a type hint is not a substitute for validating untrusted asset data.

Duck Typing and Composition-First Design

Duck typing means asking an object to perform the operation you need rather than checking its class first: if it has the right method and behavior, it can participate. Composition goes one step further by assembling behavior from independent objects:

class ExportPipeline:
    def __init__(self, validator, converter):
        self.validator = validator
        self.converter = converter

    def run(self, record):
        errors = self.validator.validate(record)
        if errors:
            return {"ok": False, "errors": errors}
        output = self.converter.convert(record["path"], record["destination"])
        return {"ok": True, "output": output}

A pipeline can receive a different validator or converter without a subclass for every combination. This is the preferred shape for many tools: small objects, narrow contracts, and dependencies passed in from the outside.

💚 Technical-Art Relevance

Asset pipelines often vary by client, file format, or target platform. Composition lets you swap a validation policy or export adapter at configuration time instead of growing a deep hierarchy such as WebGltfValidatedCompressedExporter.

Mixins, Multiple Inheritance, and MRO

A mixin is a small class intended to add one focused behavior, not to represent a complete standalone object:

class TimingMixin:
    def timed_name(self):
        return f"timed:{self.name}"

class NamedExporter:
    def __init__(self, name):
        self.name = name

class TimedNamedExporter(TimingMixin, NamedExporter):
    pass

tool = TimedNamedExporter("gltf")
print(tool.timed_name())

With multiple inheritance, Python computes an MRO, the ordered list of classes it searches for attributes and methods. super() follows that order; it does not simply mean “my one direct parent.” Cooperative multiple inheritance requires each participating method to call super() with compatible signatures. If a mixin silently assumes unrelated state or skips the chain, the design becomes fragile.

⚠️ Python Surprise: Multiple inheritance is not free composition

Mixins can be useful for tiny, orthogonal behavior, but multiple inheritance introduces MRO and cooperative-super() constraints. Prefer composition when the relationship is “has a validator” or “uses a logger,” and reserve multiple inheritance for a deliberate, documented design.

Short Drills

  1. Define a protocol for an exporter with one method, then pass two unrelated exporter classes to a function that uses that method.
  2. Refactor a hypothetical subclass with three feature combinations into a pipeline that receives three components.
  3. Write a two-class inheritance example that calls super(), then print the MRO with SomeClass.__mro__. Explain why the order matters.

Key Takeaways

  • Inheritance: reuse and override behavior, with super() following the MRO.
  • Contracts: ABCs are nominal; protocols and duck typing focus on required behavior.
  • Composition: pass small collaborators into a pipeline to keep variation flat and replaceable.
  • Multiple inheritance: useful for disciplined mixins, advanced by default, and not a replacement for ordinary composition.
